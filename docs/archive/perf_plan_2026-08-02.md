## Step 1 — BEFORE profile: queuePulse under load, without CPU starvation (15 min)

**Do not rebuild yet.**

The point of this step is to measure the animation cost *without* the confound that ruined the
2026-08-01 measurement. Then the host was at 279% of 4 cores and two thirds of the Queue Manager
jank was the main thread simply not being scheduled.

The trick: `isCurrent` is `!isComplete && i === currentIndex`, so **any** non-`COMPLETED` job row
animates its current stage — `PENDING` and `PAUSED` included. Queue a backlog and pause it, and you
get many animating rows while the worker sits idle.

1. Upload ~20 pages to a scratch chapter and start the pipeline.
2. **Immediately pause the queue globally** in the Queue Manager.
3. Confirm you have the setup you want:

   ```bash
   docker stats --no-stream manga-worker manga-backend
   ```

   **Expect:** worker under ~10% CPU. If it's still busy, a job was mid-flight — wait for it to
   finish. The whole point is an idle host.

   In the UI you should see roughly 20 job rows, each with a pulsing stage bar.

4. Start the recorder (this also smoke-tests the fixed script):

   ```bash
   ./scripts/capture-run.sh start
   ```

5. With the Queue Manager open, record a **20-second** Firefox profile. Scroll the job list slowly
   through the whole capture. Save the **lean** export (the one without hidden threads — 7-13
   threads is plenty).

6. Stop and label:

   ```bash
   ./scripts/capture-run.sh stop
   mv logs/runs/<newest> logs/runs/BEFORE-queuepulse
   ```

7. Write `logs/runs/BEFORE-queuepulse/NOTES.md`:

   ```markdown
   # BEFORE — queuePulse, paused queue, idle host
   - Bundle: QueueManager-CcIMRu8l.js (old, nested @keyframes)
   - Job rows visible: ~20, all PAUSED/PENDING, all animating
   - Worker CPU during capture: <fill in from docker stats>
   - Profile: 20s, Queue Manager open, scrolling
   ```

**Checkpoint:** `resources.csv` in that directory should show the worker near-idle for the whole
window. That file is the proof the host wasn't starved — without it the comparison is worthless.

## Step 2 — Rebuild and deploy (10-15 min)

Optional but recommended first — **enable sourcemaps**. This is the one change that unblocks the
largest unresolved item (the two Reader-bundle closures worth 2.44 s that currently read as
`io/qn</t/xe<`). In `frontend/vite.config.ts`, alongside `plugins` / `base`:

```ts
  build: {
    sourcemap: true,
  },
```

Vite emits sourcemaps as *separate* `.map` files; the JavaScript that executes is unchanged, so this
does not affect the A/B in Step 3.

Then:

```bash

docker compose up -d backend
```

## Step 4 — Throughput baseline, fully drained (30-45 min, mostly waiting)

This is the run that produces everything the 2026-08-01 runs could not. It supersedes them as the
baseline: the worker CPU cap has changed stage timings, so the old numbers are no longer comparable.

1. Queues empty (`Step 0`), nothing paused.
2. `./scripts/capture-run.sh start`
3. Upload ~20 pages. Start the pipeline. **Change nothing. Pause nothing.**
4. **Let it drain completely.** Wait until the queues are empty *and* no job is `PROCESSING`:

   ```bash
   watch -n 10 'docker exec manga-db psql -U tladmin -d manga_library -tAc \
     "SELECT status, COUNT(*) FROM jobs WHERE created_at > now() - interval '\''1 hour'\'' GROUP BY status;"'
   ```

   This is the step every previous run skipped, and it's why no page ever had a complete
   `panel-detection → ocr → layout → translation → render → qa` chain.

5. Take one 15-20 s Firefox profile mid-run of the Queue Manager under *real* load — this gives the
   starved-host counterpart to Steps 1 and 3.
6. `./scripts/capture-run.sh stop`
7. Rename to `logs/runs/BASELINE-capped-worker` and write `NOTES.md` (pages, chapter, what felt
   slow, anything odd in the UI).

**The stop output now tells you whether the run is usable.** If it prints:

```
!! NOT DRAINED: N job(s) still unfinished, M still queued.
```

then the run can't produce a time budget — wait longer and re-run. If it prints
`!! N query/queries FAILED`, tell me; that's a bug in my script fixes.

**Also check** `logs/runs/BASELINE-capped-worker/queues.csv` — it now has a `sample_ms` column. If
those values climb into the thousands, the sampler is degrading again and the timeline is coarser
than it looks.
