# F04: owner-aware OCR integration

Status: **BLOCKED**.

## Reproduced integration gap

`process_ocr` retains oriented source quads and detector polygons only when `OCR_CAPTURE_DIR` is enabled. Its normal runtime records carry axis-aligned boxes and no source-style evidence. F01 correctly treats a multi-fragment candidate without those inputs as `unknown`.

Enabling the F01 component veto with those current runtime records would therefore split every multi-fragment candidate, including legitimate dialogue. Keeping current grouping while claiming a resolved owner would contradict F01's contract. Neither outcome can satisfy F04's fresh six-page, zero-cross-owner-merge gate.

## User decision

2026-09-16: the user selected **Keep unknown**. Until source-style provenance exists, new evidence may expose unproven multi-fragment candidates as review-only, but F04 must not enable automatic owner-veto splitting or cleanup authority.

## Missing prerequisite

A bounded runtime provenance slice must establish stable fragment IDs, source-space oriented quads, validated detector-container identity, and declared source-style evidence before F01's veto can be enabled. Source-style estimation is explicitly scoped as H01 after F04; expanding F04 into H01 requires a new user-approved plan adjustment. G5/UR03 remain blocked because they require fresh six-page overlays, review-labelled merge/split counts, unresolved-fragment accounting, and dialogue coverage.
