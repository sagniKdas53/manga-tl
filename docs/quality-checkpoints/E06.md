`docker run --memory 2g --cpus 1.0` with one reusable browser context. The renderer returned source-sized lossless PNGs and no layout diagnostics:

| input | dimensions | elapsed | sampled peak RSS | PNG SHA-256 |

| ordinary synthetic scene | 320×180 | 539 ms | 150 MiB | `8f3c3d7e58d5011813321ec8cb4fa7cfde025947f71d08c006a87405fd505c0b` |
| `sample93` cold | 6764×4961 | 23,426 ms | 713 MiB | `cabbf9d34b983eec6680fb6a8cc0bf6f1faeb76a6f44737799506615c466a7f9` |
| `sample93` warm | 6764×4961 | 23,699 ms | 845 MiB | same |

845 MiB is below the tracker’s 80%-of-2-GiB headroom threshold (1,638 MiB). This is a one-context, one-CPU local measurement, not a throughput or speedup claim. Cold/warm timings are effectively equal for this source; no higher concurrency is enabled.

A large render was held in the sole context while a second ordinary request arrived. The second received HTTP 400 with `renderer context capacity is exhausted`; it did not queue silently, downsample, or use a Pillow fallback. The full retained machine-readable record is [evidence.json](../quality-runs/e06-20260915-renderer-capacity/evidence.json).
