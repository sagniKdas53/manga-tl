## E0: what was measured

The rule from the plan: a region's angle is the length-weighted angle of its OCR line pieces; a
piece shorter than 2 line-thicknesses doesn't vote; if pieces disagree by more than 6° the region
stays level; under 4° it stays level. Nothing writes an angle yet: these numbers come from the
stored OCR pieces (`ocr_regions.ownership_provenance`).

- **35 pages with both Torii and our OCR** (B stack pages): 375 boxes, error mean 1.38°, median
  0.25°, 90% within 2.8°. Of 45 Torii boxes tilted 5° or more, the rule turns 27; it turns 9 that
  Torii keeps level (mostly junk OCR such as "Nお"). Dead band 5° and minimum 1.5 thicknesses cut the
  false turns to 2.
- **The 13 test pages**: of 66 Torii-tilted boxes, 38 turned within 5° (mean error 1.8°).
  Allowing 10° of disagreement: 41.
- **Known misses**, each a design point for E2, not a threshold:
  1. One outlier column fails the agreement check for a whole bubble (sample252: a short column at
     +7.5° in a +15° bubble). Drop one outlier, or compare against the median.
  2. Korean OCR (PP-OCRv5) gives one piece per paragraph, so there is no line to measure
     (ko/sample188). Korean needs another angle source: the paragraph quad, or the glyph mask's
     main axis.
  3. Text OCR never found has nothing to turn (sample104's sash, like #245).
  4. A turned region's stored box is the level box around tilted text, too big. E2 must build the
     box from the un-rotated pieces (the plan already says so).
- **Data gotchas:** Torii's `x`/`y` are box centres; its `angle` is degrees and `rotation` the same
  in radians; fold to ±90° (a line's direction); some Torii folders lack `original.png`. Our
  provenance comes in two shapes (one fragment, or `fragments[].provenance`).

### Why no 235-page run

The plan asked for the rule to be fitted on all 270 Torii pages. That needs OCR on ~235 pages we
don't have yet: through the stack that also runs paid translation and QA, and it takes the
chrome-box hours under heat. It isn't needed:

- The rule has three numbers (dead band, minimum line, agreement). The 35 + 13 pages already give
  about 110 tilted boxes to set them, and the owner's 10 pages are a fresh check.
- What is left wrong is design (the four misses above), and a bigger sample would only show the
  same misses more often.
- D4 ships E2 behind a switch (global, with a series override), so a page set that goes wrong can
  be turned off.

## What the owner is testing

For each page, say which text should turn and roughly by how much, which should stay level, and
anything below that looks wrong. Besides the angles:

1. **E1 (rotated elements).** Rotate a text element by hand (Reshape, then the round handle), then
   in Reshape mode: the round handles sit on the outline's corners, not off to one side. Drag a
   corner: the box stays the same height and grows only along the text's own direction, with no
   jump. Undo: the outline and box come back exactly, also after a reload. Try a 30° and a 90°
   element, and an element that was never resized.
2. **Layer Undo with unsaved text (#254).** Edit a text, then press the layer Undo straight away:
   the text saves first and is not lost or overwritten. With the browser offline (DevTools →
   Network → Offline), edit a text, deselect, press layer Undo: it refuses with "an edit is still
   unsaved"; back online, Undo works and the edit is kept.
3. **F changes since your F test.** Group some layers, hide the group, and try to merge two of its
   layers across a shown layer between them: refused. Show the group, merge two layers, then
   reload and Undo: everything comes back as it was. After an Undo of a merge, text sits at the
   same size as before (no re-fit jump). (A show/hide landing exactly during an Undo is covered by a
   backend test; it can't be timed by hand.)
4. **On the E test pages, not the angle:**
   - Was the tilted text found at all? (sample104's sash wasn't.) List any missed text.
   - Is each slanted bubble one region, or split/over-merged? (Over-merged regions hold pieces at

   - OCR reading on tilted text: sample252 read Chinese-looking characters for Japanese.
   - Cleanup on diagonal text: leftover ink or smears along the slant.
   - Wallpaper text (sample92): should it be translated at all?

## How to resume

1. Read the owner's findings. Put their 10 pages through the same path: rank or pick them, copy the
   sources to chrome-box `~/Documents/docker-composes/e-rotation-20261008/<new folder>`, and upload
   them as a **new** series or chapter with `scripts/e0/upload_test_pages.py` (edit its `DONE`
   guard file and `SERIES` titles first, so it neither refuses nor reuses today's series). Never upload a page the stack has seen: a duplicate copies the old page's regions
   instead of running OCR.
2. Once OCR is done (only the `ocr` jobs matter here), add the pages to
   `scripts/e0/test_pages.tsv` and to `scripts/e0/export_regions.sh`, export, and run
   `python3 -I scripts/e0/check_test_pages.py corpus/samples test_regions.json scripts/e0/test_pages.tsv out/`.
   It prints Torii's tilted boxes beside the rule's angle and draws both on each page.
3. Settle the rule with the owner (dead band, minimum line, the outlier fix, the Korean source),
   then build **E2**: worker `merge_regions.py` and `handlers/ocr.py` write `rotation: 0.0` in six
   places today; the backend stores the region's rotation (`coordinator.rs` ~L1675) but the code
   that creates translated text (`coordinator.rs` ~L2566, ~L2939) never copies it to the text. E2
   needs both, plus `OCR_TEXT_ANGLE` (on/off) and its dead band as settings (D4: on, with the
   switch in System Settings, OCR section).
4. Merge #253 and #254 once the owner's test passes (stacked PRs merge through
   `PUT /repos/{o}/{r}/pulls/{n}/merge-async`, bottom-up).
5. Then F5 (#244), which reuses E2's box code. E3 waits for G2 (#176/#177).
